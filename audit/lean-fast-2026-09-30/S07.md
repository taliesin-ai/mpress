## Mounting and reader checkpoint

Regressions against `5bdc828` prove mounting writes into external linked output/version/snapshot/metadata destinations and protected project inputs, including links from the output into source files. It also drops nested manifest-named assets. List, Verify and Mount can observe the interval where force replacement has moved the old snapshot and has not yet promoted the new one. The original-production replay requires five failing top-level tests and rejects compilation failures: `python3 audit/lean-fast-2026-09-30/evidence/s07-mount/replay-before.py`.

Mounting now loads rooted configuration, retains the disabled-version behavior, checks the existing output protection policy and pins an output root. Metadata for a missing store uses this same output boundary. Each snapshot has one pinned root throughout verification and copy; every copied stream and HTML rewrite uses a narrow destination root. Root URL rewrites, current/version navigation, safe output/store/file aliases and ordinary metadata serialization retain their contracts. Only the root snapshot manifest is omitted; nested manifest-named assets are published.

List, Verify and Mount hold a shared stable store lock throughout each operation. Multiple readers coexist; Capture and Remove require the exclusive lock. Native Linux tests explicitly exercise reader coexistence, writer exclusion until every reader closes, and all three public readers waiting for replacement to complete. Legacy read-only stores without a lock retain supported reads when lock creation fails for lack of permission. Stores written by Capture always have the stable lock. The fallback assumes the legacy read-only store remains unchanged; cross-user writers modifying such a lockless store are not qualified.

Full public race/vet and affected final race checks pass. Tampered snapshots are rejected before their files are published. A read-only mounting directory preserves its existing file and the source snapshot.
