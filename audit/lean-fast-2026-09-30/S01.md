# Build and clean output safety — Beads mp-b52.1.1

Baseline: `74488e1b1`, which already includes the separately tracked LCP fixes. The original build/clean guards only checked lexical project containment. Configuring output as content, static, Git metadata, configuration or persistent state could delete those inputs. An output beneath an external symlinked parent also deleted external files.

The fix adds one shared configuration-aware boundary in `internal/config/output.go`. Build validates output before discovery/cache writes and again immediately before deletion; CLI clean uses the same removal operation. Both canonical containment and overlap are checked. Existing ancestors are resolved for missing output directories. Protected paths include configured content/static directories, configuration/custom CSS, Git metadata, configured translation/version stores, and persistent `.mpress` data.

The existing `.mpress/export-*` and `.mpress/live-preview` child workspaces remain usable; those exceptions never override protected source/state overlap. Other `.mpress` output targets are rejected. Internal parent/project aliases remain supported. Case aliases of existing inputs are checked using filesystem identities, while distinct names on a case-sensitive filesystem remain valid.

Deletion uses the already selected Go toolchain's `os.Root.RemoveAll`, which confines traversal to the project. A final output symlink is unlinked rather than following it during deletion. This preserves the original replacement behaviour and prevents deletion of an unrelated internal target. A regression caught an intermediate implementation violating that rule; its failing evidence is retained, and the final implementation passes.

## Scope and remaining work

This closes the build/clean data-loss defect, not the whole filesystem audit. Route escapes remain `mp-b52.1.2`; authoring confinement remains `mp-b52.1.3`; failed-build staging remains `mp-b52.1.5`. In particular, the dev server's separate preview-pool startup/cleanup uses raw removals and still needs review when sources/state overlap that pool or its parents are symlinked. That source risk was added to the existing P0 authoring task instead of describing all dev filesystem operations as safe.

The rooted API confines deletion; this report does not claim complete protection against an adversary concurrently rearranging protected directories inside the project, privileged mount manipulation, or every other read/write in the application. The original feature-freeze objective and final qualification gate remain open. No product features or third-party production dependencies were added.

Public logs and equivalence/classification data are in [evidence/s01](evidence/s01/). The root API's documented boundary and platform caveats are described in [Go's traversal-resistant filesystem API documentation](https://go.dev/blog/osroot).
